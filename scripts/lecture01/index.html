SECTION 02 · 바이브 코딩이란?

예상 시간: 6:00 ~ 15:00 (9분)

↓ 스크롤

자, 바이브 코딩이 뭔지 설명할게요.

화면에 요리사 비유가 나와 있는데, 이게 정말 딱 맞는 비유예요. ⏸ 잠깐

레스토랑에서 음식을 주문할 때 어떻게 해요? "스테이크 미디엄으로요, 감자 사이드로 주세요." 이렇게 말하잖아요. 요리사가 어떤 칼 쓰는지, 몇 도에서 굽는지 — 알 필요 없어요. 주문서만 정확하면 원하는 음식이 나와요.

바이브 코딩이 딱 그거예요. 코드는 AI가 짜요. 여러분은 "뭘 만들지, 어떤 데이터로, 어떤 기준으로, 뭘 보여줘" — 이 주문서를 정확하게 쓰는 사람이 되는 거예요.

↓ 스크롤

화면에 한 문장 정의 박스가 있어요. 천천히 한 번 읽어보세요. ⏸ 잠깐

"코드를 직접 짜는 것이 아니라, 내가 만들고 싶은 결과를 말로 설명하면 AI가 코드를 대신 만들어주는 방식."

이게 전부예요. 이 문장 하나면 충분해요.

↓ 스크롤

그 아래 세 칸짜리 비교 박스가 나와요. 기존 코딩, 바이브 코딩, 사람의 역할.

여기서 제일 중요한 게 세 번째 칸이에요. "사람의 역할 — 문제 정의, 기준 제시, 결과 검증."

바이브 코딩이라고 해서 사람이 할 일이 없어지는 게 아니에요. 오히려 더 중요한 일만 남아요. 어떤 문제를 풀지 결정하고, 어떤 기준이 맞는지 판단하고, AI가 만든 결과가 현장에서 실제로 맞는지 검증하는 것 — 이건 현장을 아는 엔지니어만 할 수 있는 일이에요.

↓ 스크롤

역할 분리 흐름도가 나와요.

엔지니어가 문제와 기준을 정의하면 → AI가 코드와 차트와 보고서 초안을 만들고 → 엔지니어가 현장 기준으로 검증하고 수정 지시를 해요.

이 세 단계가 바이브 코딩의 전체 사이클이에요. 오늘 강의도 이 흐름을 따라가요.

↓ 스크롤

전통 방식과 바이브 코딩 비교 카드가 나왔어요.

왼쪽 전통 방식 — "구현 과정을 직접 관리한다." 핵심은 어떻게 코드를 만들 것인가예요.

오른쪽 바이브 코딩 — "해결 목표를 정의한다." 핵심은 무엇을 해결할 것인가예요.

이 사고방식의 전환이 이 강의에서 제일 중요한 부분이에요.

↓ 스크롤

노란 박스, 혁신의 핵심 부분이에요. 천천히 보세요. ⏸ 잠깐

요약하면 이거예요. 코딩 실력의 출발점이 "문법 암기"에서 "문제 정의 능력"으로 바뀌었다. 그래서 첨단 공정 엔지니어한테 필요한 건 개발자가 되는 게 아니라 — AI가 일할 수 있을 만큼 정확하게 공정 문제를 설명하는 능력이에요.

SECTION 04 · 전통 코딩 vs 바이브 코딩

예상 시간: 21:00 ~ 27:00 (6분)

↓ 스크롤

비교 화면이에요.

왼쪽 전통 코딩 화면 보면, 코드 에디터에 에러 메시지가 빨갛게 떠있어요. ModuleNotFoundError: No module named 'matplotlib'.

이게 기존 코딩 방식의 현실이에요. 현장 문제 분석하려고 앉았는데, 라이브러리 설치 문제로 첫 시간을 다 써버리는 거예요. ⏸ 잠깐 코딩을 배우러 온 게 아닌데, 코드 문제에 발목 잡히는 상황이 생기는 거죠.

오른쪽 바이브 코딩 화면 — Antigravity라는 AI 분석 도구예요. 채팅창에 이렇게 입력해요. "1000개의 공정 데이터 중에서 이상점이 발생한 부분을 진단하고 그것을 시각화해줘." 그러면 가우시안 밀도 분포, 박스플롯, 진단 보고서가 나와요.

설치 에러 없어요. 라이브러리 없어요. 질문 하나로 결과 나와요.

↓ 스크롤

아래 비교표 보면 세 줄이에요.

입력 — 전통 방식은 문법, 라이브러리, 에러 메시지와 싸우고 / 바이브는 문제, 데이터, 기준, 결과물을 설명해요.

초점 — 전통은 "어떻게 코드를 만들까" / 바이브는 "무엇을 해결할까"

결과 — 전통은 코드 수정 흔적 / 바이브는 대시보드, 차트, 보고서 초안

어느 쪽이 엔지니어로서 시간을 더 잘 쓰는 건지 — 명확하죠.

SECTION 05 · 왜 중요한가?

예상 시간: 27:00 ~ 32:00 (5분)

↓ 스크롤

왜 첨단 공정기술 엔지니어한테 이게 중요한지 설명할게요.

AI는 공정 지식을 대신할 수 없어요. 어떤 공정에서 왜 이 수치가 이상한지 — 그건 현장을 아는 사람만 알아요. 근데 AI가 잘하는 게 있어요. 반복되는 데이터 정리, 초안 작성, 이상 구간 탐색. 이걸 빠르게 처리해서 — 엔지니어가 진짜 중요한 판단에 더 많은 시간을 쓸 수 있게 만들어줘요.

↓ 스크롤

비포-애프터 카드 세 개가 있어요.

반복 보고서 — 지금은 엑셀 파일 열고, 필터, 피벗, 캡처를 반복해요. AI 쓰면 — 데이터 범위와 기준을 지시하면 표, 그래프, 요약 초안이 자동으로 나와요.

이상 감지 — 지금은 관리 한계 초과 구간을 사람이 직접 찾아요. AI 쓰면 — OOC 시점, 관련 센서, 확인 질문이 한 화면에서 나와요.

회의 준비 — 지금은 불량 이미지랑 수율 로그를 따로 모아서 발표 자료를 손으로 구성해요. AI 쓰면 — 대표 이미지, 우선순위, 조치 후보가 포함된 리뷰 자료 초안이 만들어져요.

⏸ 잠깐

세 가지 다 공통점이 있어요. 기존 방식은 도구를 다루는 데 시간을 써요. 바이브 코딩은 판단에 시간을 써요.

↓ 스크롤

Target Point 박스를 한 번 보세요.

"AI를 활용해 공정 데이터 분석·보고서·이상감지를 빠르게 자동화하는 첨단 공정기술 엔지니어를 기업은 원한다."

이게 이 강의가 목표로 하는 엔지니어 모습이에요.

SECTION 06 · 첨단 공정기술 사례

예상 시간: 32:00 ~ 44:00 (12분)

↓ 스크롤

이제 실제 사례 세 가지를 볼게요. 이 부분이 오늘 강의에서 제일 중요한 파트예요.

↓ 스크롤

Case 01 — 수율 로그 자동 요약이에요.

지금 현장에서 어떻게 해요? 화면에 엑셀 파일 8개가 보여요. LINE_A, LINE_B, LINE_C... 각 파일에 1,000개 이상의 행이 있어요. 합치면 4,720개 이상의 데이터예요.

이걸 하나씩 열어서 날짜별로 필터 걸고, 전일 수율이랑 오늘 수율 비교하고, 3% 이상 하락한 셀을 눈으로 찾아요. ⏸ 잠깐 이게 30분에서 50분짜리 작업이에요.

그런데 작업지시서를 이렇게 쓰면 어떻게 돼요.

"최근 7일간 라인/공정/모델별 수율을 비교하고, 전일 대비 3% 이상 하락한 항목만 빨간색으로 표시해줘. 하락 폭 TOP5와 원인 후보, 엔지니어 확인 질문을 포함한 HTML 보고서로 만들어줘."

AI가 내놓는 결과가 화면에 나와요. A Line Array OLED-14에서 04-24일에 4.2% 하락. C Line Cell OLED-17에서 3.7% 하락. 원인 후보와 추가 확인 질문까지 정리된 보고서가 나와요.

⏸ 잠깐

여기서 핵심 포인트예요.

AI가 원인을 확정하는 게 아니에요. AI는 "먼저 봐야 할 후보"를 정리해줘요. 그 후보가 실제 원인인지 판단하는 건 공정과 설비 이력을 아는 엔지니어가 해요. 그 역할 분리가 중요해요.

↓ 스크롤

Case 02 — AOI 불량 이미지 분류예요.

AOI가 뭔지 아시죠? Automated Optical Inspection, 자동 광학 검사예요.

폴더 4개에 이미지 668장이 있어요. 하나씩 열어서 Scratch인지, Particle인지, Mura인지 눈으로 판단하고 엑셀에 기록해요. 1~2시간짜리 작업이에요.

작업지시서를 쓰면 — 668장이 24개 우선 검토 후보로 줄어요. Scratch 38건, Particle 24건, Mura 18건으로 자동 분류되고, 유형별 대표 이미지 갤러리가 만들어져요.

⏸ 잠깐

668장을 다 보는 게 아니라, 24개만 집중해서 보면 되는 거예요. 이게 시간 효율이에요.

↓ 스크롤

Case 03 — 설비 센서 OOC 감지예요.

화면에 CSV 파일 6개가 있어요. EQP-17 온도, 압력, 유량. EQP-22 온도, 압력, 유량. 각각 1분 단위로 1,440개 행이에요.

이걸 각각 열어서 이동평균 계산하고, UCL/LCL 초과 시점을 눈으로 찾아요.

작업지시서로 하면 — 센서 로그 표에서 09:40부터 Watch 신호가 뜨고, 10:00에 Pre-OOC, 10:10에 OOC가 감지돼요. 온도 88.7°C가 UCL 87°C를 초과했고, 조치 메모까지 자동으로 붙어요. "Chiller 공급 온도와 Recipe step 4 확인."

⏸ 잠깐

다시 한 번 — AI가 설비 원인을 단정하는 게 아니에요. 사람이 필터와 조건부 서식으로 찾던 OOC 후보를 먼저 정리해서 — 엔지니어의 판단 시간을 줄여주는 거예요.

SECTION 07 · 의도 설계

예상 시간: 44:00 ~ 52:00 (8분)

↓ 스크롤

이제 핵심 중의 핵심이에요. 어떻게 지시하느냐에 따라 결과가 완전히 달라진다는 걸 보여드릴게요.

화면에 두 가지 지시문이 나와 있어요.

왼쪽 — "수율 분석해줘." ⏸ 잠깐 AI가 뭐라고 해요? "수율 하락의 일반적인 원인은 장비 유지보수 지연, 원자재 오염... 어떤 라인의 데이터인가요? 기간은 얼마나 되나요?" 역질문이 돌아와요.

즉각 실행성이 12%예요. 실제로 일이 시작이 안 된 거예요.

오른쪽 — "최근 7일간 A/B/C 라인 OLED-14 수율을 비교하고, 전일 대비 3% 이상 하락한 항목만 빨간색으로 표시해줘. 하락 폭 TOP5, 원인 후보, 엔지니어 확인 질문을 HTML 보고서 형태로 만들어줘."

AI가 뭐라고 해요? "수율 분석 대시보드를 생성합니다. yield_log.xlsx → 라인/모델 필터 → diff 계산 → 빨간 하이라이트 → TOP5 추출 → dashboard.html 생성 완료."

즉각 실행성 94%예요.

⏸ 잠깐

같은 목표인데, 어떻게 쓰느냐가 결과를 만들어요.

↓ 스크롤

아래에 5가지 요소별 비교 표가 있어요. 모호한 표현 vs 좋은 표현.

문제 — "수율 분석" vs "Array 공정 A/B/C 라인의 OLED-14 수율 하락 원인 후보 확인"

데이터 — "엑셀 파일" vs "최근 14일 yield_log.xlsx, 컬럼: Date, Line, Model, Yield, Temp, Pressure, AOI Defect"

기준 — "이상한 것" vs "전일 대비 -3% 이상 또는 3일 이동평균 90% 미만이면 위험 표시"

산출물 — "보기 좋게" vs "라인별 추이 그래프, 위험 TOP5 표, 원인 후보, 확인 질문이 있는 HTML 대시보드"

검증 — "알아서" vs "데이터 누락, Lot 수 부족, Recipe 변경 여부는 검증 필요 항목으로 분리"

⏸ 잠깐

이 다섯 가지가 다 들어간 지시문이 작업지시서예요. 이걸 잘 쓰는 능력이 이 강의 전체에서 키우려는 거예요.

SECTION 08 · 미니 워크숍

예상 시간: 52:00 ~ 58:00 (6분)

↓ 스크롤

실습 파트예요.

화면에 타임라인이 있어요. 2분 문제 고르기, 3분 데이터·기준 채우기, 2분 산출물 정하기, 1분 검증 질문 추가.

지금 당장 완벽하게 채우려고 하지 않아도 돼요. 중요한 건 내 현장 업무를 AI가 이해할 수 있는 구조로 바꾸는 연습 자체예요.

↓ 스크롤

3단계 카드예요.

1단계 — 현장 문제를 한 문장으로. 예시가 나와 있어요. "CVD 이후 막두께 산포가 특정 Lot에서 커졌고, 원인이 장비인지 레시피인지 빠르게 보고 싶다." 이것처럼 구체적으로요.

2단계 — 데이터와 기준을 붙여요. 예시 보면 — "컬럼은 Lot ID, 설비 ID, Recipe, Temp, Pressure, Thickness이며 목표 막두께는 120nm ±5nm이다." 이렇게 숫자와 기준까지 들어가야 해요.

3단계 — AI에게 맡길 결과물을 지정해요. "설비별 산포 box plot, 이상 Lot 목록, 원인 후보 3개, 엔지니어 확인 질문을 포함한 HTML 리포트를 만들어줘."

↓ 스크롤

그 아래에 세 가지 유형별 워크숍 예시가 있어요. 수율 로그형, AOI 이미지형, 설비 센서형. 본인 업무와 가장 가까운 걸로 연습해보세요.

↓ 스크롤

화면에 5요소 직접 입력하기 폼이 있어요. 공정·장비·데이터, 문제 현상, 데이터 컬럼, 판정 기준, 원하는 산출물 — 이 다섯 칸을 채우면 작업지시서가 완성되고, "Claude에 복사하기" 버튼으로 바로 붙여넣을 수 있어요.

강의 끝나고 바로 해보세요. 첫 번째 AI 작업지시서, 오늘 만들어보시는 거예요.

예상 시간: 58:00 ~ 62:00 (4분)

↓ 스크롤

마지막이에요. AI에게 보내기 전 확인 체크리스트 다섯 가지예요.

하나씩 읽어볼게요.

"문제 배경: 어떤 공정/장비/데이터에서 발생한 문제인가?" — 추상적으로 쓰면 AI도 추상적으로 답해요.

"입력 데이터: 파일 형식, 주요 컬럼, 단위, 기간을 설명했는가?" — 이게 빠지면 AI가 임의로 가정해요.

"판정 기준: 정상/이상, 목표값, spec, 관리 한계를 적었는가?" — 기준 없이는 AI가 뭘 경고해야 할지 몰라요.

"출력 형식: 표, 그래프, 대시보드, 보고서 중 무엇을 원하는가?" — 원하는 형식을 말해야 원하는 형식이 나와요.

"검증 조건: 엔지니어가 다시 확인해야 할 리스크를 남겼는가?" — AI가 만든 결과를 그대로 쓰면 안 돼요. 검증 포인트를 미리 지정해두세요.
